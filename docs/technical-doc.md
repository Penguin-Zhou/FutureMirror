## 摘要

面镜 FutureMirror 面向"面试准备缺乏真实对手、反馈不可解释、改进无路径"三个痛点，用**多 Agent 圆桌协作**替代单人问答：HR、技术、压力面、观察员、教练五个角色按规则轮转分工，围绕用户上传的简历与目标岗位 JD 展开多轮模拟面试，全过程**流式打字**呈现。

系统产出三类结果：**可解释的评分报告**（五维分数 + 逐条点评 + 回答原文摘录取证）、**能力雷达可视化**、**按最弱维度排序的 Day-N 改进计划**。配套题库小测、错题本、求职看板与 AI 小助手形成"练习—评估—补强—再评估"闭环。

工程上的取舍集中在两点：**演示必须零依赖可跑**（单文件 493KB，CSS/JS 全内联，默认零外部请求，断网不断演练），以及**评分必须可核对**（每个分数都能追到具体一轮回答的原话与计算因子）。为此设计了"单文件演示版 ↔ 模块版前端"的双向机械转换（逐字节等价）、"后端真实模型 → 浏览器直连 Key → 本地 Mock"的三级降级，以及全部运行在浏览器内的 BM25 + 端侧向量混合检索。

## 1. 项目概述与目标

### 1.1 我们要解决的问题

面试准备存在三个长期存在但难以自助解决的问题：

| 问题 | 现状 | 面镜的做法 |
| --- | --- | --- |
| **没有真实对手** | 背模板、看面经，缺乏追问压力；真人模拟成本高、难以反复 | 五个 Agent 分工协作：追问、施压、观察、复盘都由不同角色承担，可无限次重跑 |
| **反馈不可解释** | 打分类产品只给总分或几句话点评，不知道扣分在哪 | 五维分数每条都附带**计算依据**（量词数、STAR 词、口头禅、技能命中、防御性表述）与**原话摘录取证** |
| **改进行动缺方法** | "多练表达"这类建议无法落地 | 按最弱三个维度自动分配 3/2/1 项任务，生成带日期的 Day-N 学习路径 |
| **演示环境不可控** | 依赖云 API 的产品在赛场网络不稳时直接白屏 | 三级降级：后端真实模型 → 浏览器直连 Key → 本地 Mock；断网也能完整走完流程 |

### 1.2 目标用户

- **求职者 / 应届生（终端用户）**：需要低成本、高频次的模拟面试与可执行的改进计划。
- **评委与开发者（演示态）**：需要在不装环境、无网络、无 Key 的情况下，3 分钟内看懂系统做了什么、怎么做的。

### 1.3 功能清单

| 编号 | 模块 | 能力 |
| --- | --- | --- |
| 1 | 简历—岗位匹配 | 解析简历文本与目标 JD，输出匹配度、命中技能、能力缺口（本地规则计算，无外部依赖） |
| 2 | 多 Agent 模拟面试 | 五角色追问 / 压力面 / 连环追问，流式打字输出，支持中途停止与重开 |

| 4 | 可解释评分报告 | 五维打分 + 雷达图 + 逐维点评 + 最近 4 轮原话取证 + `weakest` 最弱维度 |
| 5 | 学习路径 | 基于最弱三维按 3/2/1 配额生成 Day-N 任务清单 |

## 2. 系统架构与技术选型

### 2.1 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│  浏览器                                                        │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────────┐ │
│  │ 单文件演示版  │  │  模块版前端   │  │  Next.js 完整版       │ │
│  │ (index.html) │  │ (frontend/)  │  │  (app/)              │ │
│  └──────┬───────┘  └──────┬───────┘  └──────────┬───────────┘ │
│         │ 三种前端共享同一套业务逻辑（store / auth / features） │
└─────────┼─────────────────┼─────────────────────┼─────────────┘
          │ HTTPS / SSE     │                     │ Route Handlers
          ▼                 ▼                     ▼
   ┌────────────────────────────────────┐   ┌──────────────────┐
   │  FastAPI 后端（backend/）           │   │  多模型路由 + RAG │
   │  JWT 鉴权 · SQLite · SSE 代理       │   │  + Zod 契约      │
   │  ─ 评分引擎 scoring.py              │   └──────────────────┘
   └───────────────┬────────────────────┘
                   │ httpx 流式转发（Key 只在服务端环境变量）
                   ▼
            智谱 GLM-4-Flash（OpenAI 兼容）
```

**关键：后端是"可选增强"而不是"必需依赖"。** 前端每次调用前探测 `http://localhost:8000` 的 `/api/health`，在线则对话 / 登录 / 报告生成全部走后端（Key 零接触浏览器）；离线则按 3.4 节的降级链自动回退，功能不减、只是数据来源不同。

### 2.2 为什么先做"单文件优先"

| 约束 | 影响 | 对策 |
| --- | --- | --- |
| 赛场网络不可控 | 依赖 CDN / 云 API 的产品可能整页白屏 | 全部 CSS/JS 内联，字体走系统栈，默认零外部请求 |
| 评委临时查看 | 不愿先执行 `npm install` | 双击 HTML 即可完整走完流程；内载演示数据与 Mock 模型 |
| 断网要能演示 | 评审可能要求关网演示 | Mock 模型内置完整问答语料，功能链路不因断网中断 |
| 又要便于二次开发 | 单文件 493KB 不利于阅读与协作 | 用 `split-frontend.js` 机械拆出 `frontend/` 模块版，`build-demo.js` 反向合并回单文件 |

### 2.3 单文件版与模块版的双向转换

这是本项目的工程基础，也是"用单文件交付、按模块维护"的前提：

```
public/futuremirror-demo.html
        │  split-frontend.js（按"版本横幅"机械切分）
        ▼
frontend/  ── 27 个 JS 模块 + 3 层 CSS + build-manifest.json
        │  build-demo.js（反合并：link 序列 → <style>，script 序列 → 单 <script>）
        ▼
public/futuremirror-demo.html      （除 1 行 hashchange 监听注册随 handler 归位外，逐字节一致）
```

三条约束保证了等价性可验证：

1. **`.gitattributes` 锁定 LF**（`* text=auto eol=lf`），避免 Windows 上的 CRLF 破坏逐字节比对；
2. `npm run build:demo`（即 `build-demo.js`）必须产出与仓库中完全一致的文件，CI 里用 `git diff --exit-code` 卡住；
3. `test-frontend-modules.js` 用 jsdom 真实加载模块版，验证它能独立启动（28 项断言）。

### 2.4 一次面试的数据流

```
① 上传简历 + 目标 JD
      ▼
② 本地匹配引擎解析 → match_score / 命中技能 / 能力缺口       （纯浏览器，零网络）
      ▼
③ 创建会话   POST /api/interviews            （后端离线时生成本地 interviewId）
      ▼
④ 五个 Agent 按轮转策略出牌，逐字流式渲染到面试台
   · HR：简历追问与动机校验
   · 技术：围绕简历项目深挖实现细节
   · 压力面：质疑方案、压缩时间、制造冲突
   · 观察员：记录关键行为，不直接发问
   · 教练：阶段复盘，给出下一轮提示
      ▼
⑤ 每轮回答写入 localStorage；后端在线时按 seq 幂等批量同步
      ▼
⑥ 结束 → 评分引擎：五维打分 + 点评 + 最近 4 轮取证 + Day-N 计划
      ▼
⑦ 报告渲染（雷达图）＋ 服务端落库（幂等覆盖，重复打开不重复计数）
```

### 2.5 技术选型

| 层 | 选型 | 理由 | 替代方案为何没选 |
| --- | --- | --- | --- |
| 演示前端 | 原生 HTML/CSS/JS（无框架） | 单文件自包含、可被任意静态托管、启动 0ms | React + Vite：需要构建产物，无法"双击即开" |
| 模块版 | 原生 ES 风格全局脚本 + `<script>` 顺序加载 | 与单文件版保持逐字节等价，无打包要求 | ESM `import`：单文件合并需改写 import 语句，破坏等价性 |
| 后端 | FastAPI + SQLAlchemy + PyJWT | 交互式文档自动生成；同步 ORM 在 SQLite 下足够；JWT 无状态便于部署 | Flask / Express：无原生 OpenAPI，SSE 实现更啰嗦 |
| 数据库 | SQLite（`futuremirror.db`） | 单文件落盘，答辩时可直接 `sqlite3` 查询证明"真实持久化" | Postgres：需要额外服务，增加演示环境不确定性 |
| 流式 | SSE（Server-Sent Events） | 单向流式足够，HTTP 原生、无需额外协议库 | WebSocket：双向用不上，握手与部署复杂度更高 |
| 模型 | 智谱 GLM-4-Flash（OpenAI 兼容协议） | 免费额度 + 兼容 SDK，替换为其他 OpenAI 兼容模型仅需改 base_url | 固定厂商 SDK：协议锁定，迁移成本高 |
| 端侧向量 | Transformers.js · `Xenova/all-MiniLM-L6-v2` | 浏览器内推理，384 维，Apache-2.0，零 API 成本且离线可跑 | 远程 embedding API：断网即失效，且有调用成本 |
| 完整版 | Next.js + TypeScript + Zod + Zustand | Route Handlers 统一前后端契约；Zod 校验输入输出；生产形态可平滑演进 | 继续用原生：完整版需要类型安全与工程约束 |

## 3. 核心算法

本章是技术深度的集中体现：四套算法/机制全部可以在源码中定位、可以当场用数据验证，且**前端本地实现与后端服务端实现共用同一套规则**（`backend/app/scoring.py` 的注释明确写明了这一点，二者可互相校验）。

### 3.1 多 Agent 圆桌协作机制

不是"调用五次大模型"，而是**有角色分工、有轮转规则、有状态记忆**的协作协议。

| Agent | 职责 | 提问风格 | 输出去向 |
| --- | --- | --- | --- |
| HR 面试官 | 简历真实性校验、动机与文化匹配 | 开放式："说一个你最失败的项目" | 面试记录 + `notes` 标注 |
| 技术面试官 | 围绕简历项目深挖实现细节 | 追问式："为什么不用延迟双删？" | 计入"内容深度"维度 |
| 压力面试官 | 制造冲突、压缩时间、质疑结论 | 敌意式："这个方案我看不出价值" | 计入"抗压表现"维度 |
| 观察员 | 只记录不提问，标记行为特征 | — | 写入 `notes`（如"出现防御性表述"） |
| 教练 | 阶段复盘、给出下一轮提示 | 复盘式 | 生成阶段性建议，不评分 |

**轮转规则**：开场由 HR 建立基线 → 技术面按简历技能点深挖（每回答中出现的新名词可成为下一个追问锚点）→ 中段插入压力面 → 教练阶段性小结 → 循环，直到达到轮次上限或用户主动结束。每个角色都有**版本化 Prompt**（可在"Prompt 查看器"页面核对），Prompt 的改动会被记录，从而解释不同版本产出的差异。

**连环追问**：当回答中出现可展开的技术名词或量化指标（如"QPS 从 200 提升到 1200"），该名词进入追问队列，由对应角色的下一轮提问消费。这让面试表现出"听得懂上一句"的连贯性，而不是固定题库顺序放题。

### 3.2 证据驱动的可解释评分引擎

评分规则在 `backend/app/scoring.py`，前端 demo 的 `scoreSession` 与之逐条对应。

**五个维度与计算因子**

| 维度 | key | 基线 | 正向因子 | 负向因子 |
| --- | --- | --- | --- | --- |
| 内容深度 | `depth` | 48 | 数字量词 ×2.2（上限 22）、技能词典命中 ×2.5（上限 18）、≥4 轮 +8 | — |
| 结构逻辑 | `logic` | 46 | STAR 关键词（背景/目标/负责/通过/最终/结果/因此/于是）×4（上限 30）、≥3 轮 +8 | — |
| 语言表达 | `expression` | 88 | — | 口头禅（然后/那个/就是）×5（上限 24）、短回答（<40 字）×4 |
| 岗位匹配 | `fit` | 52 或 55 | 有匹配报告时：`52 + match_score × 0.4 + 命中技能数`（上限 +10）；无报告时：`55 + 命中 ×2`（上限 20） | — |
| 抗压表现 | `stress` | 72 | — | 防御性表述（"不是我的"/"但是"等）×6（上限 20）；压力轮存在时短回答 ×3（上限 12），否则固定 −6 |

**融合外部信号**

- `code_score`（代码沙箱通过率）参与深度：`depth = clamp(depth × 0.8 + code_score × 100 × 0.2)`
- `match_gaps`（简历—岗位匹配缺口）写入 `fit` 维度的点评文本，例如"基于匹配报告：匹配分 90，缺口 Kubernetes、Go"

**为什么这样设计**

1. **`_clamp` 落在 `[30, 96]`**：刻意保留上下限，避免出现 0 分或满分这种"看不出差异"的极端值，也让异常输入不至于击穿评分曲线。
2. **总分 = 五维平均**（`round(sum(dims)/5)`），而不是加权和：维度权重差异会掩盖短板，平均值让"偏科"直接反映在总分上。
3. **每条点评绑定触发条件**（如 `digit_count >= 4` 才有"量化数据充分"的表述），评委可反查：给定一段回答，能手工复算每个维度。
4. **学习路径按最弱三维配 3/2/1**：`plan` = 排序后最弱三个维度各取其建议池前 3/2/1 条 + 2 条通用建议，生成 `Day 1…Day 8` 的任务表，每条带所属维度标签。
5. **取证**：`evidence` 取最后 4 轮，保留 `agent / quote（截 60 字）/ note`，报告里每条结论都能追到原话。

**这套规则的边界**：它是规则驱动的评分（可解释、可复算），不是模型打分。好处是断网也能出报告、结果稳定可答辩；代价是无法评估语义层面的"答得是否切题"，这一点在 5.4 节列为已知边界。

### 3.3 检索层：BM25 + 端侧向量混合检索

AI 小助手的检索**不是关键词匹配**，而是词面 + 语义双路召回后归一融合，**全部在浏览器内完成**（零后端、零 API、离线可跑）。

| 环节 | 实现 | 关键参数 |
| --- | --- | --- |
| 分词 | 英文/数字整词 + 中文 bigram | 与完整版 `lib/ai/rag.ts` 同策略，中文无空格也能召回 |
| 词面召回 | BM25（`bm25Score`） | `k1=1.5`、`b=0.75`；IDF 恒正（`log(1+…)` 防负权）；标题字段重复计入 = 权重 ×2 |
| 语义召回 | Transformers.js · `Xenova/all-MiniLM-L6-v2` | 384 维，`pooling=mean` + L2 归一，浏览器内推理 |
| 向量库 | `localStorage["fm_kb_vec_v1"]`（40 条预计算向量 + 元信息） | 二次访问"缓存命中"零推理；条目数与知识库不符时**拒绝加载**，避免脏索引 |
| 离线兜底 | n-gram hashing 向量（`hashEmbed`，256 维，有符号特征哈希 + L2 归一） | 无模型文件 / CDN 不可达时自动启用，状态条如实标注"非语义" |
| 融合 | `score = 0.6 × cosine + 0.4 × bm25_normalized` | 两路各自 min-max 归一后加权；纯语义召回设余弦门槛（MiniLM 0.15 / hashing 0.32）防噪声 |
| 可解释 | 每条引用显示 `bm25 0.82 · cos 0.61 · 融合 0.74` | 评委可当场核对分数，不是黑箱"相似度" |

**为什么用 BM25 而不是纯向量**：纯向量会把"Redis 过期策略"和"Redis 集群方案"都召回成高分，因为语义接近但问题完全不同；BM25 对精确术语敏感。反过来，纯 BM25 召回不到"缓存和数据库怎么保持一致"这种同义改写。两者融合后两个方向的失效都被抑制。

**为什么不调用在线 embedding**：一是断网演示会失效；二是 API 成本与延迟不可控；三是端侧推理天然保护隐私（简历文本不出浏览器）。

> 完整版 `lib/ai/rag.ts` 在此基础上升级为 pgvector + RRF + Rerank；演示版保留的是同一套**思路**在浏览器内的等价实现。

### 3.4 三级降级容错

```
① 后端真实模型    GET /api/health → {ok:true, llm_ready:true}
                  SSE 流式代理，API Key 只存在于服务端环境变量
        │ 超时 / 5xx / Key 未配置
        ▼
② 浏览器直连 Key  用户在设置里自带 Key，浏览器直接请求模型 API
                  （用户明确粘贴后启用，凭据不写入网盘以外的任何持久化位置）
        │ Key 为空 / 网络不可达 / 请求失败
        ▼
③ 本地 Mock       内置语料 + 模板化生成 + 流式打字效果，功能完整可演示
```

配套的两个设计保证了"降级可感知、但不打断"：

- **页面顶部如实显示当前模式**（如"本地 Mock 模式"），不误导用户以为是真实模型输出；
- **`doLogin` 等路径加了 `if (!fmApi.healthAt)` 守卫**，避免每次操作都触发一次无谓的健康检查，也避免旧版同步测试链因无条件 `await` 而断裂。

### 3.5 简历—岗位匹配引擎

`heuristicParse` 是纯本地规则引擎：从简历文本抽取技能（对照词典，含 React / Kubernetes / RAG / Prompt 等 33 项常用技能与技术词），与 JD 文本中的技能要求做交集与差集，输出：

- **匹配分**：命中 ∩ 要求的加权比例（示例输入下实测 75 分）；
- **命中技能**：双方共有的技能列表；
- **能力缺口**：JD 要求而简历未体现的技能，这些缺口会流入 3.2 节 `fit` 维度的点评。

它是确定性的、可离线运行的，也能被替换为 LLM 版本而**不改动下游**——下游只消费 `match_score` 与 `match_gaps` 两个字段。
