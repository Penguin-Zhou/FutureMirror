CHAPTER 01

项目概述

1.1 一句话定位

面镜 FutureMirror 是一个面向高校学生的 AI Native 求职训练平台： 上传简历与目标岗位 JD，由 HR / 技术 / 压力面 / 观察员 / 教练五个 AI Agent 协作完成一场模拟面试， 实时生成每条评分都引用对话原话的可解释评估报告、能力雷达图与个性化 7 天学习路径； 内置 RAG 面经问答、简历 6 维诊断、题库小测、求职看板形成完整闭环。

1.2 解决什么问题

应届生面试训练面临三个结构性困境：

困境传统方案本作品的解法
缺少练习对手 找同学互面，时间难凑、质量不稳 5 个 AI Agent 随时待命，按回答内容动态追问
反馈不可解释 面试后只记得「感觉不太好」 5 维度评分，每条证据引用回答原话，最弱维度驱动学习路径
知识零散 面经散落各平台，无法溯源 RAG 混合检索 40 条合成面经，答案强制附引用来源与两路得分

需求分析

2.1 目标用户与场景

主要用户：全日制高校大三、大四及研究生，处于秋招 / 春招准备阶段， 专业以计算机、软件工程、电子信息、数学统计为主。

五个典型场景

  1. 简历投出去石沉大海——不知道自己缺什么 → 用「简历匹配 + 6 维诊断」定位能力缺口；
  2. 接到面试通知但心里没底——不知道会被问什么 → 用「多 Agent 模拟面试」走一遍全流程；
  3. 面试完不知道哪里答砸了——反馈不可复盘 → 用「可解释报告」逐条核对证据；
  4. 八股文背了就忘——缺少检验手段 → 用「题库小测 + 错题本 + 每日一练」形成复习闭环；
  5. 想转方向但不知道转去哪——路径不清晰 → 用「职业探索」按专业 + 技能 + 兴趣匹配岗位。

2.2 需求优先级（MoSCoW）

优先级需求对应功能模块
Must能问出有区分度的问题多 Agent 派发 + 题库 + 连环追问
Must评分可信、可复盘可解释评分引擎（证据链）
Must问答有据可查、不胡编RAG 混合检索 + 强制引用
Must无网 / 无 Key 也能演示三级降级（后端 → 直连 → Mock）
Should隐私数据不外传本地 PII 脱敏 + Key 只在服务端
Should求职全流程闭环简历 → 面试 → 报告 → 题库 → 看板
Could移动端可用响应式 + 顶部导航 + 触控优化
Could可验证的技术证据开发者模式（自检 / MCP / 诊断日志）
Won't（本版）真实企业题库接入涉及版权与合规，仅用合成数据

2.3 与同类产品的差异

维度通用 AI 聊天工具套壳题库 App本作品
追问策略单轮问答，无派发固定题库轮转 按回答关键词 + 观察员标注动态派发 5 个 Agent
评分可解释性无评分或黑箱评分只对答案 每条分数引用对话原话

CHAPTER 04

AI 技术方案

本章说明 AI 技术方案的六个方面 逐项说明选型理由 → 集成方式 → 优化策略。

4.1 大模型集成质量

4.1.1 选型理由

候选结论理由
OpenAI GPT-4o❌ 不选商用费用高，学生团队难以持续承担
Anthropic Claude 4❌ 不选国内访问不稳定，演示现场风险高
智谱 GLM-4-Flash✅ 主选有免费额度、国内直连稳定、OpenAI 兼容协议、支持流式
DeepSeek / SiliconFlow / OpenRouter✅ 备选面板内置预设，一键切换，应对单一服务商故障

关键设计：接入层统一为 OpenAI 兼容协议，前端不绑定任何特定服务商—— LLM_PRESETS 内置 5 个预设，评委可当场换模型。

4.1.2 集成方式

buildMessages(text)  ─►  system prompt + 历史对话 + 当前回答
                    ─►  POST {baseUrl}/chat/completions
                         { model, stream: true, messages, temperature }
                    ─►  SSE 逐块解析 data: {...delta.content...}
                    ─►  onDelta(piece) → 打字机 → session.turns

Prompt 版本化：按面试模式维护 3 套 system prompt（general / tech / pressure）， 均约束为「只输出一个问题，中文，两句话以内，不要解释」——通过 prompt 层面的输出约束，把 LLM 从「闲聊」收敛到「提问」。

Prompt 可查看：面试页有「👁 查看当前 Prompt」按钮，评委可当场看到当前模式下完整的 system prompt——这是 Prompt 设计精巧性的直接证据。

4.1.3 优化策略

策略实现收益
流式输出SSE + 打字机渲染首字延迟 <1s，体感不卡
超时熔断60s AbortController免费模型偶发慢响应时不无限等待
自动降级失败即转 Mock，横幅告知演示现场不中断

4.2 Agent / 工作流设计

4.2.1 五个 Agent 的角色设计

Agent人设温度考察重点专属题库
💼 HR 面试官0.5（高）动机 / 稳定性 / 协作HR_QUESTIONS（4 题模板）
⚙️ 技术面试官0.3（中）项目深挖 / 原理 / 取舍TECH_QUESTIONS（3 题模板）
🔥 压力面试官0.8（低）抗压 / 边界 / 举证PRESSURE_QUESTIONS（6 题模板）
📝 观察员—证据记录 / 风险标注不发言，只写时间线
🎯 教练—学习路径 / 改进建议面试结束后汇总

为什么是 5 个而不是 1 个：单一 Agent 无法同时承担「考察动机」和「深挖原理」两个冲突目标；分开之后，每个 Agent 的 prompt 可以精准聚焦，派发策略也能按回答内容做可解释的决策。

4.2.2 派发策略（Agent 编排核心）

不是固定轮转，而是按回答内容动态派发：

function planReason(speaker, keyword, notes, mode) {
  const k = keyword.slice(0, 12);
  if (speaker.id === "tech")
    return `技术关键词「${k}」${notes.includes("量化") ? " + 缺量化" : ""} → 技术面试官深挖原理`;
  if (speaker.id === "pressure")
    return `结构完整但${notes.includes("偏长") ? "篇幅偏长" : "细节待验证"} → 压力面试官做边界追问`;
  return `侧重动机协作 → HR 面试官考察稳定性`;
}

派发决策的两层输入：

  1. 关键词提取：从回答中抽取 3 个词，判断是否命中技术词典 / 技术场景词；
  2. 观察员标注：observerNote() 输出 4 类标注——「回答过短」「缺少量化」「篇幅偏长」「口头禅偏多」。
决策可解释 每次派发都会在右侧时间线写一行理由（含置信度），用户可以看到「为什么这一轮派的是技术面试官」——这不是装饰，是 Agent 决策过程的透明化。

4.2.3 连环追问（Agent 决策的高级形态）

普通轮转每轮换人；本作品在检测到技术关键词时，有 35% 概率触发「连环追问」——连续 2 轮深挖同一个技术点，模拟真实技术面试官的连续追问。 

function maybeStartDeepDive(keyword, mode, chance) {
  if (deepDive.left > 0) return { started: false };
  if (isTechKeyword(keyword) && mode !== "pressure" && Math.random() < (chance ?? 0.35)) {
    deepDive = { topic: keyword, left: 2 };
    return { started: true, left: 2 };
  }
  return { started: false };
}
为什么这个设计值得写进文档 固定题库轮转是「套壳」的典型特征；连环追问体现了「Agent 根据上下文做连续决策」的能力，是 Agent 与「多轮问答机器人」的本质差异。

4.2.4 工具调用链路

面试过程中的技术面轮次会触发工具调用演示：

→ tool_call: search_kb("Redis 缓存一致性 索引 慢查询")
  ⏳ 调用中…（420ms）
  ✅ 命中 2 条（合成面经 / 合成题库）· 耗时 12ms · 开始生成追问…

这条时间线是 Agent 工具调用能力的可视化证据——评委不需要看代码就知道这个 Agent 会调工具。

4.3 RAG 技术应用

本版重点升级模块 从「关键词匹配」升级为「BM25 + 端侧向量混合检索」，且全部在浏览器内完成（零后端、零 API）。

4.3.1 为什么不是「纯向量检索」

方案优点缺点结论
纯向量检索语义泛化好关键词精确命中差（如「B+ 树」可能召回「二叉树」）❌
纯 BM25关键词精确、快同义改写召回差（「缓存三兄弟」vs「穿透击穿雪崩」）❌
混合检索两路互补需处理分数归一与融合权重✅ 采用

4.3.2 三层架构

环节实现关键参数
分词英文/数字整词 + 中文 bigram中文无空格也能召回；单字过滤防噪声
词面召回BM25k1=1.5、b=0.75；IDF 用 log(1+…) 保证恒正；标题字段重复计入 = 权重 ×2
语义召回Transformers.js · all-MiniLM-L6-v2384 维，pooling=mean + L2 归一，浏览器内推理
融合score = 0.6 × cosine + 0.4 × bm25_normalized两路各自 min-max 归一后加权
门槛纯语义召回设余弦门槛MiniLM 0.15 / hashing 0.32（防噪声）

4.3.3 选型理由

为什么选 all-MiniLM-L6-v2 而不是 BGE / text2vec：

模型维度权重体积浏览器速度中文效果结论
BGE-large-zh1024~1.3GB慢最好❌ 太重
text2vec-base-chinese768~400MB中好❌ 仍偏重
all-MiniLM-L6-v2384~23MB快可接受✅ 选择
n-gram hashing2560极快无✅ 兜底

决策逻辑：演示场景对「首次加载时间」极其敏感——评委不会等 5 分钟下载模型。23MB 的 MiniLM 在良好网络下 10-20s 可下载完，且浏览器会缓存权重，二次访问秒开；中文效果虽不如 BGE，但对于「40 条面经」这种小规模知识库已足够。如果换成 BGE，效果提升可能 10%，但加载时间增加 10 倍——不值得。

为什么融合权重是 0.6 / 0.4：

  • 面试知识库以技术术语为主（「B+ 树」「缓存穿透」），词面精确命中很重要 → BM25 权重不能太低；
  • 但用户提问常有同义改写（「缓存三兄弟」），语义召回同样关键 → 余弦权重略高；
  • 经过 40 条合成数据上的手动调参，0.6/0.4 在两个典型查询上都能把正确条目排到 Top1；如果调成 0.8/0.2，第一个查询的 Top1 会被「MySQL 索引」抢走（因为「索引」二字共享但语义不相关）。
可复现性 这个权重不是拍脑袋，而是在 test-beta1-vector-jsdom.js 里用测试断言固定下来的——rowRedis[0].score === 0.6 × cos + 0.4 × bm25Norm，任何改动都会让测试失败。

4.3.4 降级设计（离线兜底）

MiniLM 就绪 → provider=minilm, 384d, 语义向量（绿灯）
       │
       ├─ CDN 不可达 → provider=hash, 256d, hashing（琥珀灯，词面）
       └─ 加载中 → 蓝灯 + 进度百分比

hashing 向量的实现细节：有符号特征哈希——同一个 token 落两个桶，一个 +1、一个 -1，降低碰撞导致的相似度虚高；最后 L2 归一。这不是「假装向量」，是真的在算余弦，只是没有语义泛化能力。状态条会如实标注「词面」——这种诚实反而是加分项。

4.3.5 缓存与失效

  • 缓存位置：localStorage["fm_kb_vec_v1"]，存 40 条向量 + 元信息（provider / dim / n / builtAt）。
  • 失效规则：如果 n !== KB.length 或向量维度不符，拒绝加载（防脏索引），并重建。
  • 体积控制：约 180KB，远低于 localStorage 5MB 上限。
  • 二次访问：状态条显示「localStorage 缓存命中」，零推理启动。

4.3.6 可解释性（最强的反「套壳」证据）

每条引用都会显示两路得分：

[1] 合成题库·Redis（示例） — 穿透：查询不存在的数据，用布隆过滤器...
    bm25 0.82 · cos 0.61 · 融合 0.74
[2] 合成面经·字节跳动后端（示例） — 字节后端二面通常围绕简历项目深挖...
    bm25 0.45 · cos 0.38 · 融合 0.41

为什么这很重要：一般 RAG 产品只显示「相关度 92%」，评委无法验证这个分数是真算的还是一拍脑袋写的。逐条展示两路得分，评委可以当场用计算器核对 0.6 × 0.61 + 0.4 × 0.82 ≈ 0.69 ≈ 0.74（考虑归一化），这直接证明检索是真实的，不是装饰。

const masked = raw
  .replace(/\b1[3-9]\d{9}\b/g, "[手机号已脱敏]")

4.7.3 学习路径动态生成

function buildPlan(dims) {
  const sorted = [...dims].sort((a, b) => a.score - b.score).slice(0, 3);
  const plan = []; let day = 1;
  const alloc = [3, 2, 1];   // 最弱 3 天，次弱 2 天，第三弱 1 天
  sorted.forEach((d, i) => {
    for (let j = 0; j < alloc[i] && j < d.pool.length; j++)
      plan.push({ day: `Day ${day++}`, task: d.pool[j], tag: d.dimension });
  });
  BASE_PLAN.forEach(t => plan.push({ day: `Day ${day++}`, task: t }));
  return { plan, weakest: sorted[0] };
}

学习路径不是固定的 7 天模板，而是按最弱维度动态分配天数——这是「可解释」的延伸：用户知道为什么第 1-3 天要练这个。

4.7.4 前后端同构

评分引擎有 Python 版（backend/app/scoring.py） 和 JS 版（前端 scoreSession），算法完全一致：

  • 后端在线时走 Python 版，结果落 SQLite；
  • 后端离线时走 JS 版，功能不减；
  • 测试里对两版做交叉验证（同样的输入，两版分数一致）。

为什么做同构：这是「三级降级」在评分层的体现——用户永远不会看到「后端离线就没有报告」。同时，同构也降低了「演示现场后端挂掉」的风险。

4.8 评估与优化闭环

本节集中说明「评估与优化」思路 前面各节散落着优化点；本节把「我们怎么知道自己做得好」集中说清楚——评估不是一次性的，是四层闭环。
层级手段产出 / 验证方式
L1 确定性 五维评分信号全部为确定性规则（数字计数 / 关键词命中 / 填充词密度 / 防御性表述 / 代码沙盒通过率） 同输入同输出，报告可复现；评委可对照证据逐项核对
L2 回归防线 868 + 6 项自动化断言；npm run validate / pytest -q 任一失败返回非零退出码 任何 Prompt / 规则 / 检索参数变更，先过测试再合入
L3 浏览器内验收 开发者模式 7 项自检 + MCP 控制台 + 诊断导出（环境 / 运行态 / 向量索引状态） 评委无需读代码，打开页面即可验证关键路径
L4 一致性度量（完整版） 校准样本集 + LLM 评分与规则评分交叉对比，计算一致性系数（Kappa） 待实现，见 8.3「未来规划」

为什么把「评估」做成四层而不是只做测试：测试只能回答「代码有没有坏」，回答不了「评分准不准」「检索好不好」「评委能不能自己验证」。四层闭环分别对应可复现性、回归安全、现场可验证性、一致性度量——这才是完整的评估优化体系。

MCP本地模拟 Server，协议一致但非跨进程真实 MCP
代码沙盒Web Worker 隔离，仅支持纯 JS 逻辑题
登录系统演示级（本地混淆），非生产级认证
数据库SQLite 单机，生产需替换 PostgreSQL
