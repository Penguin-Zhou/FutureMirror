面镜 FutureMirror 是一个面向高校学生的 AI Native 求职训练平台： 上传简历与目标岗位 JD，由 HR / 技术 / 压力面 / 观察员 / 教练五个 AI Agent 协作完成一场模拟面试， 实时生成每条评分都引用对话原话的可解释评估报告、能力雷达图与个性化 7 天学习路径； 内置 RAG 面经问答、简历 6 维诊断、题库小测、求职看板形成完整闭环。

2.1 目标用户与场景

主要用户：全日制高校大三、大四及研究生，处于秋招 / 春招准备阶段， 专业以计算机、软件工程、电子信息、数学统计为主。

  3. 面试完不知道哪里答砸了——反馈不可复盘 → 用「可解释报告」逐条核对证据；

3.5 技术选型论证：为什么是原生栈，而不是 Next.js

作品的前端技术选型为原生 JavaScript（ES2022）+ HTML + CSS 手写设计系统，后端为 FastAPI 薄接入层。 这是一个需要正面回答的选择——现代前端框架是全栈 AI 应用的主流方案，本节逐条说明取舍依据，以及为此付出的工程补偿。

3.5.1 三条决定性约束

约束如果用框架会怎样原生栈的解法
必须能离线演示 Next.js / Vite 产物依赖构建环境与运行时（Node、.next 目录、Node 静态服务）；访客电脑断网或未装 Node 时，演示直接失败 构建脚本把 38 个模块与 3 层 CSS 反合并成单个 648KB 的 HTML，双击即可运行，无 npm、无构建、无服务器
评分引擎要能端侧独立跑 框架的 SSR / RSC 心智模型会把「评分」推向服务端，端侧只能拿结果，无法解释过程 同一套五维规则在前端与后端各实现一份且逐条对拍（report.js ↔ scoring.py），断网时前端引擎照常出分，且两边对同一输入的输出一致
演示要能证明「代码可解释」 框架的抽象层（编译器、路由约定、Server Components）会带来大量「不是我写的代码」，深挖追问时解释成本高 全部 38 个模块均为手写、无编译转换，scripts/split-frontend.js 可把单文件产物逐字节还原成源码，源码与交付物一一对应

3.5.2 用工程补偿换掉框架红利

放弃框架意味着失去组件化、类型约束、代码规范等生态红利。这些不是被忽略，而是被显式补齐：

框架通常提供的本项目的补偿手段可当场验证
组件化 / 模块边界38 个模块按「core / data / features / dev」四层划分，由 build-manifest.json 声明加载顺序npm run build:demo
代码规范（ESLint）ESLint 10 扁平配置；因模块共享同一全局作用域，用 gen-eslint-globals.js 从源码自动提取 472 个共享符号做白名单，no-undef 仍然有效npm run lint → 0 error
格式化（Prettier）Prettier 3 托管脚本层与配置层；前端源码因 build-manifest 行号基准与格式敏感断言而不纳入重排，理由写在 .prettierignore 注释里npm run format:check
类型约束（TypeScript）不引入编译步骤，改用 jsconfig.json + JSDoc + types/models.d.ts：编辑器内获得补全与跳转，运行时契约由 1513 条断言与后端 Pydantic 模型双向保证npm run verify
状态管理（Zustand 等）自研 store（约 30 行）：sessionStorage 优先、localStorage 回落，键名按用户 id 加前缀实现数据隔离切换账号后数据不串号

3.5.3 已采用的「推荐栈」能力

在推荐技术栈中，凡是与本作品业务相关的条目均已真实接入，且都能在演示中触发：

  • Transformers.js 端侧推理：Xenova/all-MiniLM-L6-v2（384 维）在浏览器内算句向量，模型权重随站点分发，推理 0 请求；无模型文件时自动降级为 n-gram hashing（256 维）
  • Web Speech API：面试页提供语音作答（ASR），并用 speechSynthesis 朗读面试官问题（TTS，零成本、无外部请求）
  • SSE 流式：对话逐 token 渲染；WebSocket：实时看板数据流，网关不支持升级时自动降级为 REST 轮询
  • 浏览器本地持久化：会话与历史报告存 localStorage/sessionStorage，不依赖登录也能演示
  • 商用 LLM API：智谱 GLM-4-Flash（免费额度），服务端代理转发，Key 不下发浏览器
结论：技术选型的判断标准是「能否把作品的核心价值稳定交付给访客」，而非「是否命中推荐列表」。本作品的核心价值是可解释的评分过程 + 端侧可独立运行 + 全部代码可还原可解释，这三点恰好与重框架的方向相反，因此选择原生栈，并用 ESLint / Prettier / JSDoc / 1513 条断言把工程规范补齐到可审查的水平。

4.2 Agent / 工作流设计

本节为总览；算法级细节（两层调度 / 连环追问状态机 / SSE 事件协议 / 与模板轮转的差异）见 7.1 多 Agent 协作调度算法。

4.2.1 五个 Agent 的角色设计

Agent人设温度考察重点专属题库
💼 HR 面试官0.5（高）动机 / 稳定性 / 协作HR_QUESTIONS（4 题模板）
⚙️ 技术面试官0.3（中）项目深挖 / 原理 / 取舍TECH_QUESTIONS（3 题模板）
🔥 压力面试官0.8（低）抗压 / 边界 / 举证PRESSURE_QUESTIONS（6 题模板）

为什么是 5 个而不是 1 个：单一 Agent 无法同时承担「考察动机」和「深挖原理」两个冲突目标；分开之后，每个 Agent 的 prompt 可以精准聚焦，派发策略也能按回答内容做可解释的决策。

4.2.2 派发策略（Agent 编排核心）

不是固定轮转，而是按回答内容动态派发：

function planReason(speaker, keyword, notes, mode) {
  const k = keyword.slice(0, 12);
  if (speaker.id === "tech")
    return `技术关键词「${k}」${notes.includes("量化") ? " + 缺量化" : ""} → 技术面试官深挖原理`;
  if (speaker.id === "pressure")
    return `结构完整但${notes.includes("偏长") ? "篇幅偏长" : "细节待验证"} → 压力面试官做边界追问`;
  return `侧重动机协作 → HR 面试官考察稳定性`;
}

派发决策的两层输入：

  1. 关键词提取：从回答中抽取 3 个词，判断是否命中技术词典 / 技术场景词；
  2. 观察员标注：observerNote() 输出 4 类标注——「回答过短」「缺少量化」「篇幅偏长」「口头禅偏多」。
决策可解释 每次派发都会在右侧时间线写一行理由（含置信度），用户可以看到「为什么这一轮派的是技术面试官」——这不是装饰，是 Agent 决策过程的透明化。

4.2.3 连环追问（Agent 决策的高级形态）

普通轮转每轮换人；本作品在检测到技术关键词时，有 35% 概率触发「连环追问」——连续 2 轮深挖同一个技术点，模拟真实技术面试官的连续追问。 

function maybeStartDeepDive(keyword, mode, chance) {
  if (deepDive.left > 0) return { started: false };
  if (isTechKeyword(keyword) && mode !== "pressure" && Math.random() < (chance ?? 0.35)) {
    deepDive = { topic: keyword, left: 2 };
    return { started: true, left: 2 };
  }
  return { started: false };
}
为什么这个设计值得写进文档 固定题库轮转是「套壳」的典型特征；连环追问体现了「Agent 根据上下文做连续决策」的能力，是 Agent 与「多轮问答机器人」的本质差异。

4.3.3 选型理由

为什么选 all-MiniLM-L6-v2 而不是 BGE / text2vec：

模型维度权重体积浏览器速度中文效果结论
BGE-large-zh1024~1.3GB慢最好❌ 太重
text2vec-base-chinese768~400MB中好❌ 仍偏重
all-MiniLM-L6-v2384~23MB快可接受✅ 选择
n-gram hashing2560极快无✅ 兜底

决策逻辑：演示场景对「首次加载时间」极其敏感——访客不会等 5 分钟下载模型。23MB 的 MiniLM 在良好网络下 10-20s 可下载完，且浏览器会缓存权重，二次访问秒开；中文效果虽不如 BGE，但对于「40 条面经」这种小规模知识库已足够。如果换成 BGE，效果提升可能 10%，但加载时间增加 10 倍——不值得。

为什么融合权重是 0.6 / 0.4：

  • 面试知识库以技术术语为主（「B+ 树」「缓存穿透」），词面精确命中很重要 → BM25 权重不能太低；
  • 但用户提问常有同义改写（「缓存三兄弟」），语义召回同样关键 → 余弦权重略高；
  • 经过 40 条合成数据上的手动调参，0.6/0.4 在两个典型查询上都能把正确条目排到 Top1；如果调成 0.8/0.2，第一个查询的 Top1 会被「MySQL 索引」抢走（因为「索引」二字共享但语义不相关）。
可复现性 这个权重不是拍脑袋，而是在 test-beta1-vector-jsdom.js 里用测试断言固定下来的——rowRedis[0].score === 0.6 × cos + 0.4 × bm25Norm，任何改动都会让测试失败。

4.3.4 降级设计（离线兜底与同源托管）

站点自托管权重就绪 → provider=minilm, 384d, 语义向量（绿灯）
       │
       ├─ 同源 / Pages models/ 不可达 → 依次探测 hf-mirror → huggingface
       ├─ 全部不可达 → provider=hash, 256d, hashing（琥珀灯，词面）
       └─ 加载中 → 蓝灯 + 进度百分比

权重随站点自托管（同源读取）：端侧模型权重（all-MiniLM-L6-v2，约 23MB）与 ONNX Runtime 的 wasm 运行时（ort-wasm-simd.wasm / ort-wasm.wasm，约 18MB）均随演示站点同源发布，浏览器从站点自身 models/ 目录读取，不再依赖 huggingface.co / hf-mirror 等外网源。这彻底消除了此前「权重下载失败（Failed to fetch）」与「CORS 缺失 / CDN 抖动导致 backend 初始化失败」两类问题——线上两个站点已实测可直接加载。

探测链路：loadVecModel 先按 同源 models/ → Pages models/（ACAO:*）→ hf-mirror → huggingface 顺序探测 config.json（8s 超时），命中同源即设 env.backends.onnx.wasm.wasmPaths = 同源 ort/，否则回退 CDN；权重源全部不可达时才降级为 n-gram hashing 向量。hashing 向量用有符号特征哈希（同一 token 落两桶，+1 / -1）降低碰撞虚高，最后 L2 归一——是真的在算余弦，只是没有语义泛化能力。状态条会如实标注「词面」——这种诚实反而是加分项。

4.3.5 缓存与失效

  • 缓存位置：localStorage["fm_kb_vec_v1"]，存 40 条向量 + 元信息（provider / dim / n / builtAt）。
  • 失效规则：如果 n !== KB.length 或向量维度不符，拒绝加载（防脏索引），并重建。
  • 体积控制：约 180KB，远低于 localStorage 5MB 上限。
  • 二次访问：状态条显示「localStorage 缓存命中」，零推理启动。

4.3.6 可解释性（最强的反「套壳」证据）

每条引用都会显示两路得分：

[1] 合成题库·Redis（示例） — 穿透：查询不存在的数据，用布隆过滤器...
    bm25 0.82 · cos 0.61 · 融合 0.74
[2] 合成面经·字节跳动后端（示例） — 字节后端二面通常围绕简历项目深挖...

4.7.3 学习路径动态生成

function buildPlan(dims) {
  const sorted = [...dims].sort((a, b) => a.score - b.score).slice(0, 3);
  const plan = []; let day = 1;
  const alloc = [3, 2, 1];   // 最弱 3 天，次弱 2 天，第三弱 1 天
  sorted.forEach((d, i) => {
    for (let j = 0; j < alloc[i] && j < d.pool.length; j++)
      plan.push({ day: `Day ${day++}`, task: d.pool[j], tag: d.dimension });
  });
  BASE_PLAN.forEach(t => plan.push({ day: `Day ${day++}`, task: t }));
  return { plan, weakest: sorted[0] };
}

学习路径不是固定的 7 天模板，而是按最弱维度动态分配天数——这是「可解释」的延伸：用户知道为什么第 1-3 天要练这个。

层级手段产出 / 验证方式

7.1.2 两层调度：模式层轮转 + 内容层派发

调度不是一层，而是两层串联——先按面试模式确定轮转骨架，再按回答内容做单次派发决策：

层输入算法输出
模式层面试模式 + 轮次 turnpickSpeaker(turn, mode)：O(1) 查表（comprehensive 按 [hr,tech,pressure] 轮转；tech 每 3 轮插入 HR；pressure 每 4 轮插入技术；gentle 恒定 HR）候选面试官
内容层最近回答的关键词 + 观察员标注planReason()：技术词命中 → 技术面试官深挖；结构完整但缺量化/偏长 → 压力面试官边界追问；否则 → HR 考察动机实际发言者 + 可解释理由 + 置信度
 
function planReason(speaker, keyword, notes, mode) {
  const k = keyword.slice(0, 12);
  if (speaker.id === "tech")
    return `技术关键词「${k}」${notes.includes("量化") ? " + 缺量化" : ""} → 技术面试官深挖原理`;
  if (speaker.id === "pressure")
    return `结构完整但${notes.includes("偏长") ? "篇幅偏长" : "细节待验证"} → 压力面试官做边界追问`;
  return `侧重动机协作 → HR 面试官考察稳定性`;
}
// 置信度：min(95, 60 + turn * 6) —— 轮次越多，画像越全，决策越自信

每次派发都会在面试间右侧时间线写一行决策理由 + 置信度，例如「📋 决策：技术关键词「Redis 缓存一致」 + 缺量化 → 技术面试官深挖原理（置信度 78%）」。Agent 的每次「换人」都有据可查——这是 Agent 决策过程的透明化，不是装饰。

7.1.3 连环追问：从「轮转」到「连续决策」

检测到技术关键词时，有 35% 概率触发连环追问——连续 2 轮深挖同一技术点，模拟真实技术面试官的追击：

function maybeStartDeepDive(keyword, mode, chance) {
  if (deepDive.left > 0) return { started: false };        // 已在追问中，不叠加
  if (isTechKeyword(keyword) && mode !== "pressure" && Math.random() < (chance ?? 0.35)) {
    deepDive = { topic: keyword, left: 2 };                // 锁定主题，再挖 2 轮
    return { started: true, left: 2 };
  }
  return { started: false };
}

固定题库轮转是「套壳」的典型特征；连环追问体现了 Agent 根据上下文做连续决策的能力，是 Agent 与「多轮问答机器人」的本质差异。

7.2 RAG 混合检索与重排序策略

7.2.1 六阶段检索管线

检索不是「调一次 embedding API」，而是六个阶段、每阶段产出均可展示为证据的管线（端侧演示页 frontend/js/data/kb.js 与服务端 lib/ai/rag.ts 同策略实现）：

阶段名称实现可展示证据
①分词英文/数字整词 + 中文 bigram 切分分词结果（开发者模式）
②词面召回BM25：k1=1.5、b=0.75，标题字段重复计入 = 权重 ×2，IDF 恒正逐条 bm25 分
③语义召回MiniLM-L6-v2（384d，浏览器内推理）；无模型文件降级 n-gram hashing（256d，纯本地）逐条 cos 分 + 向量提供者
④融合两路各自 min-max 归一后加权：0.6×cos + 0.4×bm25Norm；纯语义召回设余弦门槛（MiniLM 0.15 / hashing 0.32）融合分
⑤重排对融合召回的 Top-8 候选用 5 个可解释词面/结构特征精排（见 7.2.6）重排分 + 五特征分解
⑥引用构建Top-k 条目编号成上下文，答案必须标注来源，降低幻觉引用列表

7.2.2 分词：为什么是 bigram 而不是接分词器

中文用户输入通常不带空格（「字节后端二面一般问什么」）。无分词器方案下，对含中文的 token 追加二元词组（bigram）是 CJK 检索的标准做法：「缓存穿透」切出「缓存 / 存穿 / 穿透」，召回「Redis 缓存穿透/击穿/雪崩区别」条目的同时，单字词被过滤（长度 < 2 丢弃）防噪声。零依赖、毫秒级、与服务端策略一致。

7.2.3 为什么不是「纯向量检索」

方案优点缺点结论
纯向量检索语义泛化好关键词精确命中差（「B+ 树」可能召回「二叉树」）❌

7.2.4 端侧语义通道与四级降级

MiniLM 权重（23MB）的获取链路按国内网络实测排序：① 站点同源 models/ → ② GitHub Pages models/（带 ACAO:*）→ ③ hf-mirror.com → ④ huggingface.co；运行时库 similarly 多 CDN 备选（fastly 节点国内实测最快），单源 10s 超时即切换。全部不可达时降级 hashing 向量（门槛抬高到 0.32，因为它没有真实语义能力），检索链路不中断。40 条向量预计算一次写入 localStorage，二次访问零推理。

7.2.5 加权融合

两路分数各自 min-max 归一后加权：score = 0.6 × cos + 0.4 × bm25Norm。余弦权重更高——语义通道解决「换一种说法」的召回，词面通道保证精确命中；纯语义召回的条目须过余弦门槛，防止 hashing 兜底时噪声混入。

7.2.6 五特征重排：召回管「相关」，重排管「排序」

动机：加权融合隐含假设「余弦高」与「词面准」等价重要，但面试场景里「标题命中查询意图」几乎总是更强信号——用户搜「MySQL 索引」，标题含这四个字的条目应排在只在正文提及的条目前面。重排阶段把这些可解释特征显式建模：

7.3 评分引擎设计与校准过程

7.3.1 设计目标

评分引擎要回答四个问题：① 可解释（每个分数能追溯到对话原话）；② 可复现（同一输入永远同一输出，不靠模型运气）；③ 双引擎同构（前端本地引擎与服务端引擎逐位一致，支撑三级降级）；④ 对匹配报告开放（简历匹配分作为先验进入拟合维度，而非另起一套）。规则引擎（而非让 LLM 直接打分）是同时满足四者的唯一选择。

7.3.2 五维信号设计

内容深度25%数字个数（×2.2 上限 22）、技术词命中（×2.5 上限 18）、轮次 ≥4 +8、代码沙盒通过率（×0.8/0.2 融合）4+ 量化且 3+ 技术词
结构逻辑20%STAR 词命中（背景/目标/负责/通过/最终/结果/因此/于是）×4 上限 30命中 3+
语言表达15%口头禅（然后/那个/就是）×5 上限 24、短答数（<40 字）×4口头禅 ≤2 且无短答

7.3.3 边界裁剪的设计理由

所有维度分裁剪到 [30, 96]：下限 30——再差的回答也有保底，避免「零分挫败」吓退用户；上限 96——不留满分，保留「还能更好」的成长空间，也与学习路径的「补强」叙事一致。总分 = 五维均值（半价向上舍入）。

7.3.4 校准过程：四步，含一次真实缺陷修复

  1. 规则来源：信号不是拍脑袋——量化数据（STAR 面试法的 Result 可验证化）、STAR 结构词、口头禅密度、防御性表述，分别对应面试评估中内容、结构、表达、抗压四类公认维度。
  2. 双引擎对拍：backend/scripts/calibrate_scoring.py（服务端）与 scripts/calibrate-scoring.js（前端 jsdom）共用同一份标准样本 calibration-cases.json（5 个答题质量递进的样本），逐维度比对。
  3. 发现并修复舍入分歧：对拍首跑发现 C1/C5 的「内容深度」双引擎差 1 分。根因：Python 内置 round() 是银行家舍入（90.5 → 90），JS Math.round 是半价向上（90.5 → 91）——评分真值恰好落在 .5 边界（48 + 22 + 5×2.5 + 8 = 90.5）。修复：服务端改用 floor(v + 0.5) 与前端逐位一致。对拍从 3/5 变为 5/5 完全一致。这个缺陷靠肉眼读代码发现不了，是对拍方法论的价值证明。
  4. 不变量固化：单调性（答题质量提升 → 总分提升）、维度分离（每个维度只对目标特征敏感）、确定性（重复评分一致）、边界（全部落在 [30,96]）写成 backend/tests/test_calibration.py，11 条断言常驻回归。
